The main class that is used to use Carbon is the [`Client`](/api/carbon/client) class. Everything all connects to this one class, and it is the main instance for your bot.

## Creating a Client

```ts title="src/index.ts"
const client = new Client({
		baseUrl: " ... ",
		deploySecret: " ... ",
		clientId: " ... ",
		publicKey: " ... ",
		token: " ... ",
}, [new PingCommand()])
```

Here we have created a client with the following options:

- `baseUrl`: The relative base URL of your app
- `deploySecret`: The deploy secret of your bot, used as a password for deploying commands and other sensitive matters
- `clientId`: The Discord client ID of your bot
- `publicKey`: The Discord public key of your bot
- `token`: The Discord token of your bot

And we have also provided it with a list of commands, which in this case is just the `PingCommand` we created earlier.

## Event Queue Options

The client can be configured with an event queue to control how gateway events are processed.

```ts title="src/index.ts"
const client = new Client({
		baseUrl: " ... ",
		deploySecret: " ... ",
		clientId: " ... ",
		publicKey: " ... ",
		token: " ... ",
		eventQueue: {
				maxQueueSize: 10000,
				maxConcurrency: 50,
				listenerTimeout: 30000,
				listenerConcurrency: 10,
				yieldIntervalMs: 0,
				logSlowListeners: true,
				slowListenerThreshold: 1000
		}
}, [new PingCommand()])
```

- `maxQueueSize`: Maximum number of events that can be queued before backpressure is applied
- `maxConcurrency`: Maximum number of concurrent event processing operations
- `listenerTimeout`: Maximum time in ms a single listener can take before timing out
- `listenerConcurrency`: Maximum number of listeners processed at the same time per event
- `yieldIntervalMs`: Yield to the event loop after this many ms of listener work
- `logSlowListeners`: Whether to log slow listeners
- `slowListenerThreshold`: Threshold in ms for logging slow listeners

Guidance:

- Use lower `listenerConcurrency` (1-5) for CPU-heavy or sync I/O handlers, higher for mostly async work.
- Set `yieldIntervalMs` to 10-50ms for long-running handlers to reduce event loop starvation, or keep 0 for maximum throughput.

## Runtime Profiles

Carbon has two runtime profiles:

- `"serverless"` (default)
- `"persistent"`

Profiles set sensible defaults for queue budgets, concurrency, retries, and timeouts.

```ts title="src/index.ts"
const client = new Client({
    baseUrl: " ... ",
    deploySecret: " ... ",
    clientId: " ... ",
    publicKey: " ... ",
    token: " ... ",
    runtimeProfile: "serverless"
}, [new PingCommand()])
```

If you already know your runtime, set it explicitly.

## Request Scheduler Options

You can tune request behavior through `requestOptions.scheduler`.

Important detail: this is **not** a single global one-at-a-time queue. Carbon runs multiple request workers (`maxConcurrency`) and schedules work across lanes/routes. It still keeps one in-flight request per Discord rate-limit bucket.

```ts title="src/index.ts"
const client = new Client({
    baseUrl: " ... ",
    deploySecret: " ... ",
    clientId: " ... ",
    publicKey: " ... ",
    token: " ... ",
    requestOptions: {
        runtimeProfile: "serverless",
        scheduler: {
            maxConcurrency: 4,
            maxRateLimitRetries: 2,
            lanes: {
                critical: { weight: 8, maxQueueSize: 2000 },
                standard: { weight: 2, maxQueueSize: 1500, staleAfterMs: 20000 },
                background: { weight: 1, maxQueueSize: 600, staleAfterMs: 7500 }
            }
        }
    }
}, [new PingCommand()])
```

Lane quick-reference:

- `critical`: interaction callback/defer/update
- `standard`: user-facing message send/edit/follow-up
- `background`: background/admin/fetch

## Logging

Carbon uses a logger for its own warnings and errors. The default logger writes to `console` and prefixes messages with `[Carbon]`.

You can pass a partial logger if you want logs to go somewhere else. Any methods you omit fall back to the default console logger.

```ts title="src/index.ts"
const client = new Client({
    baseUrl: " ... ",
    deploySecret: " ... ",
    token: " ... ",
    logger: {
        error: (message, ...data) => {
            myLogger.error({ message, data })
        },
        warn: (message, ...data) => {
            myLogger.warn({ message, data })
        }
    }
}, [new PingCommand()])
```

Available logger methods:

- `debug(...data)`
- `info(...data)`
- `warn(...data)`
- `error(...data)`

`requestOptions.logger` can also be set if you are creating or tuning the request client separately.

## Error Output

Discord API failures throw `DiscordError`. The error keeps Discord's documented fields available:

- `status`: HTTP status code
- `discordCode`: Discord JSON error code, when present
- `errors`: mapped nested form errors, when Discord returns an `errors` object
- `rawBody`: the raw Discord error body, kept available for debugging

For form body errors, the error message includes the top-level Discord message plus mapped field paths, codes, and messages.

```txt
Invalid Form Body (400 Bad Request, Discord code 50035)
- options.0.name: This field is required (BASE_TYPE_REQUIRED)
```

Rate limits throw `RateLimitError` when request queuing is disabled. It follows Discord's rate-limit response and headers:

- `retryAfter`: `retry_after` seconds
- `global`: whether the limit is global
- `scope`: `X-RateLimit-Scope` (`user`, `global`, or `shared`)
- `bucket`: `X-RateLimit-Bucket`
- `limit`: `X-RateLimit-Limit`
- `remaining`: `X-RateLimit-Remaining`
- `reset`: `X-RateLimit-Reset`
- `resetAfter`: `X-RateLimit-Reset-After`
- `method` and `url`: the request that hit the limit

Both Carbon error classes provide `toJSON()` for structured logging.

## Event Queue Lanes

`eventQueue.lanes` gives you per-lane control over queue size, concurrency, timeout, and max event age.

Event processing is parallel too. Each lane has its own concurrency budget (`maxConcurrency`), and each event can process listeners concurrently (`listenerConcurrency`).

```ts title="src/index.ts"
const client = new Client({
    baseUrl: " ... ",
    deploySecret: " ... ",
    clientId: " ... ",
    publicKey: " ... ",
    token: " ... ",
    eventQueue: {
        lanes: {
            critical: {
                maxQueueSize: 12000,
                maxConcurrency: 40,
                listenerTimeout: 20000,
                listenerConcurrency: 10,
                maxEventAgeMs: 60000
            },
            background: {
                maxEventAgeMs: 10000
            }
        }
    }
}, [new PingCommand()])
```

Timeouts include `abortSignal` in listener data so handlers can stop downstream work cleanly when supported.

## Runtime Metrics

Need a quick runtime snapshot?

```ts title="src/index.ts"
const metrics = client.getRuntimeMetrics()
console.log(metrics)
```

You get:

- request scheduler metrics (depth, lane counts/drops, oldest age)
- event queue metrics (depth, lane stats, drops, timeouts)
- gateway forwarder delivery metrics (if plugin is attached)
